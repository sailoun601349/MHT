## 1. 现状问题盘点（先看清要解决什么）

### 1.1 与本需求直接冲突的架构短板

| # | 问题 | 代码依据 | 影响 |
|---|---|---|---|
| A1 | **单管理员模型，无角色概念** | `app/models/admin.py` 无 `role` 字段；`app/__init__.py:_seed` 只 seed 一个管理员 | 无法区分「超级管理员」与「普通管理员」 |
| A2 | **订单无责任人归属** | `app/models/order.py` 无 `owner`/`owner_admin_id` 字段 | 无法按管理员隔离订单 |

| A4 | **术语混乱** | 代码与 UI 用「专属代码」，用户口中叫「口令」 | 认知不一致，需统一为「登录密码」 |
| A5 | **凭据语义需重定义** | `app/config.py:43-45` 默认 `13800138000` / `change-me-now` | 与「写死超级管理员」语义要对齐 |

### 1.2 既有技术债（并行处理）

- **P0**：备份未运行、无 systemd 自愈、公网明文 HTTP（`error.log` 已见 SSH 扫描与 WORKER TIMEOUT）
- **P1**：无 CSRF、金额 `Float` 精度、无 `order_logs` 留痕、下单可重复提交、无 git、弱默认凭据
- **P2**：列表 N+1 查询、`/uploads/` 无鉴权、查询码可穷举、上传仅查后缀、缺筛选/导出等

> 本需求新增「管理员管理」「专属链接」「数据隔离」「自助改密」等更多 POST 接口与权限边界，**P1 中的 CSRF 与鉴权会更突出**，建议与本次一并规划。

## 2. 问题陈述（Problem Statement）

当前系统只有一个管理员，所有订单混在一个列表里。当猕猴桃销售由**多人分别推广**（分销员/亲友各自带客源）时，无法知道「订单是谁带来的」，也无法让每个人只看自己的订单。

**不解决的代价**：① 无法激励与核算分销；② 所有人共享一份订单数据，误操作/隐私风险；③ 无法沉淀「谁带来多少单」的运营数据。

## 3. 目标（Goals）

1. **两级角色**：内置 1 个超级管理员（`13800138000`），可创建/删除/停用多个普通管理员。
2. **专属链接获客**：普通管理员生成自己的链接 `http://49.232.88.86:18805/<专属短码>`（默认手机号后 4 位），顾客经链接下单即归属该管理员；无链接下单归属超级管理员。
3. **数据隔离**：普通管理员只能看自己名下订单；超级管理员看全部。
4. **责任可追溯**：订单列表/详情展示「订单责任人（管理员手机号）」。
5. **账号自助**：所有管理员可自助修改登录密码；超级管理员可代为重置、停用/启用、删除管理员。
6. **术语统一**：全站「口令/专属代码」统一为「登录密码」。

## 4. 非目标（Non-Goals，本期明确不做）

1. **不做多级权限/角色扩展**（只有「超级」与「普通」两级）。
2. **不做链接点击统计/转化漏斗**（不统计打开次数/转化，仅做归属）。
3. **不做管理员间订单转移**（除「删除管理员时订单归超级管理员」这一兜底外，不提供手动转移）。
4. **不做短信/邮件通知、不做支付**。
5. **不改查询码生成规则**（继续全局顺序号，查询码仍全局唯一）。

## 5. 用户故事（User Stories）

**超级管理员**
- 作为超级管理员，我要用固定账号（`13800138000` / 登录密码）登录，以便统一管理整个系统。
- 作为超级管理员，我要能新增普通管理员（手机号 + 初始密码），以便分发获客权。
- 作为超级管理员，我要能停用/启用、删除普通管理员账号，以便管理分销员生命周期。
- 作为超级管理员，我要能代为重置任意管理员登录密码，以便处理密码遗忘。
- 作为超级管理员，我要能自助修改自己的登录密码。
- 作为超级管理员，我要能查看所有订单并看到每笔订单的责任人，以便掌握全局。

**普通管理员**
- 作为普通管理员，我要用超级管理员分配的账号登录，以便进入自己的后台。
- 作为普通管理员，我要能查看/复制自己的专属链接 `http://49.232.88.86:18805/<我的短码>`（后 4 位，一眼可辨识），以便分享给顾客。
- 作为普通管理员，我要能自助修改登录密码，以便保障账号安全。
- 作为普通管理员，我要在自己的订单列表只看到「经我链接下单」的订单，以便专注自己的客户。
- 作为普通管理员，我要在订单列表看到自己的手机号作为责任人，以便确认归属。

**顾客（普通用户）**
- 作为顾客，我要打开管理员分享的链接后只需输入手机号即可下单，以便简单完成购买。
- 作为顾客，我要像现在一样用「手机号 + 查询码」查询自己的订单，以便追踪物流。

## 6. 需求拆解与验收标准

### 6.1 P0 — 必须（缺了无法上线）

**R1 超级管理员写死**
- 内置超级管理员：手机号固定 `13800138000`，登录密码默认 `change-me-now`（首次启动 seed，之后可自助改密）。
- `admins` 增加 `role` 字段；`13800138000` 首次启动自动创建并标记 `super`。
- 验收：
  - [ ] 全新数据库首次启动后，`13800138000` 存在且为 `super`，可用 `change-me-now` 登录。
  - [ ] 普通管理员无「管理员管理」入口，且后端拒绝其访问。

**R2 术语统一为「登录密码」**
- 全站 UI、flash 提示、README、CLI 文案中「专属代码 / 口令」→「登录密码」。
- 验收：
  - [ ] 登录页 label 为「登录密码」，错误提示不再出现「专属代码/口令」。
  - [ ] 数据库字段可保留 `admin_code_hash`（内部实现细节），对外语义统一。

**R3 超级管理员管理管理员**
- 新增「管理员管理」页（仅超级管理员可见）：列表展示手机号、角色、状态（启用/停用）、创建时间、专属短码、操作按钮。
- 创建管理员：输入手机号 + 初始密码（手机号合法且不重复），创建时自动生成专属短码（默认手机号后 4 位）。
- 重置密码：超级管理员对任意普通管理员直接设新密码（无需旧密码）。
- 停用/启用：停用后该管理员不能登录、其短码链接失效、名下订单保留；可重新启用。
- 删除：删除前二次确认；若名下有订单，其订单归属转移给超级管理员。
- 验收：
  - [ ] 超级管理员可新增管理员，重复手机号被拒绝并提示。
  - [ ] 普通管理员访问管理员管理页 → 403 或不可见。
  - [ ] 新管理员可用「手机号 + 初始密码」登录。
  - [ ] 停用后该管理员无法登录、其短码链接跳转提示「链接无效」；启用后恢复。
  - [ ] 删除有订单的管理员 → 二次确认 → 其订单责任人变为超级管理员。
  - [ ] 超级管理员账号 `13800138000` 不可删除/停用。

**R4 普通管理员专属链接（专属短码）**
- 每个普通管理员拥有唯一「专属短码」，默认 = 其手机号后 4 位（4 位数字），链接为 `http://49.232.88.86:18805/<短码>`（如 `.../2025`）。
- 短码规则：纯数字，**全局唯一**；默认后 4 位，允许管理员自定义（用于强化辨识度）。
- 碰撞处理（自动）：若「手机号后 4 位」已被占用，自动在后 4 位末尾追加递增数字直至唯一 —— 例：第一个 `1234`，第二个冲突的 `1234` 自动变为 `12341`，第三个再冲突变为 `12342`，依此类推。
- 管理员后台「我的专属链接」：展示完整链接 + 复制按钮 + 自定义短码（唯一）。
- 超级管理员**无专属链接**（其入口即根路径）。
- 验收：
  - [ ] 普通管理员可查看/复制自己的专属链接，短码一眼可辨识（后 4 位）。
  - [ ] 后 4 位冲突时自动追加递增数字（1234→12341→12342…），保证全局唯一。
  - [ ] 管理员自定义短码后，旧短码访问提示「链接无效」。
  - [ ] 超级管理员后台无「专属链接」入口（或明确显示「您使用根路径接单」）。

**R5 专属链接下单归属（含无链接兜底）**
- 顾客访问 `http://49.232.88.86:18805/<短码>` → 服务端校验短码（有效且管理员启用）→ 记录归属 → 进入下单流程。
- 顾客直接访问根路径 `http://49.232.88.86:18805/`（无短码）→ 下单归属**超级管理员**。
- 订单落库时写入 `owner_admin_id`。
- 验收：
  - [ ] 顾客经管理员 A 短码下单，订单归属 A。
  - [ ] 无链接直接下单，订单归属超级管理员。
  - [ ] 经管理员 B 短码下单，归属 B，互不干扰。
  - [ ] 短码无效/已停用 → 提示「链接无效」并跳转首页，不产生归属错误。

**R6 数据隔离**
- 普通管理员订单列表/详情仅见 `owner_admin_id = 自己` 的订单。
- 超级管理员可见全部订单。
- 隔离**后端强制**（不能只靠前端隐藏）。
- 验收：
  - [ ] 管理员 A 登录看不到 B 的订单；直接访问 B 的订单详情 URL 被拒绝（403）。
  - [ ] 超级管理员能看到 A 与 B 的全部订单。

**R7 订单责任人展示**
- 订单列表（桌面表格 + 手机卡片）增加「责任人」列/字段，显示对应管理员手机号。
- 详情页显示责任人。
- 验收：
  - [ ] 每笔订单明确显示责任管理员手机号。
  - [ ] 无归属历史订单（迁移回填）显示超级管理员手机号。

**R8 自助修改登录密码（所有管理员）**
- 新增「修改密码」入口（所有登录管理员含超管可见）：输入「当前密码 + 新密码 + 确认新密码」。
- 校验当前密码正确、新密码符合强度、两次一致 → 更新哈希。
- 验收：
  - [ ] 管理员可自助改密，改密后需用新密码重新登录。
  - [ ] 当前密码错误 → 拒绝并提示。
  - [ ] 超级管理员同样可自助改密。

### 6.2 P1 — 应该（体验/加固，核心功能可先不依赖）

- **R9 登录密码强度与初始密码展示**：初始密码明文展示给创建者（用于转告），落库仅存哈希；新密码设置长度下限。
- **R10 责任人筛选**：订单列表支持按「责任人」筛选（超级管理员常用）。
- **R11 首次登录强制改密**（可选）：普通管理员用初始密码首次登录时提示改密。

### 6.3 P2 — 未来（架构上先留余地）

- 订单在管理员间手动转移（超级管理员操作）。
- 链接点击/下单转化统计看板。
- 管理员提成/结算报表。

## 8. 核心流程设计

### 8.1 角色与链接对照

```
admins
├─ 13800138000   role=super   登录密码 change-me-now(可自助改)
│     链接 = http://49.232.88.86:18805/  （根路径，无短码）
│     权限：看全部订单 · 创建/删除/停用管理员 · 代改密码
│     接单：顾客直接访问根路径下单即归其名下
└─ 138xxxxxxx    role=admin   登录密码(超管分配初始值，可自助改)
      短码 = 手机号后4位（如 2025）
      链接 = http://49.232.88.86:18805/2025
      权限：只看自己名下订单 · 复制/自定义自己的短码
      不能：查看他人订单、管理其他管理员
```

### 8.2 专属链接下单链路

```
普通管理员A 登录 → 「我的专属链接」 → 复制 http://49.232.88.86:18805/2025
        ↓ 分享给顾客（微信等）
顾客 打开 http://49.232.88.86:18805/2025
        → 校验短码 2025（有效且 A 启用）→ session 记 ref_admin=A → 302 到 /
        → 顾客输入手机号 → 下单页 → 提交
        → 服务端读 ref_admin → Order.owner_admin_id = A
        ↓
管理员A 订单列表 = WHERE owner_admin_id = A
超级管理员 订单列表 = 全部（不筛选）
```

### 8.3 归属解析规则（下单时）

| 场景 | owner 归属 |
|---|---|
| 访问过有效 `/<短码>` 且管理员启用 | 该管理员 |
| 未访问链接（直接根路径 `/`） | 超级管理员 |
| 短码无效 / 管理员已停用 | 提示「链接无效」，按「无链接」归超级管理员 |

> 说明：归属以「本次会话最近一次访问的有效链接」为准；同浏览器先开 A 链接再开 B 链接 → 归 B（后访问者优先），属可接受的个人项目设定。

### 8.4 账号生命周期

```
超级管理员创建(手机号+初始密码)
   → 自动生成专属短码(默认后4位，冲突则自动追加递增数字)
   → 普通管理员登录 → 自助改密 / 复制或自定义短码
   → 超级管理员可：代改密码 / 停用(短码失效+禁登录) / 启用 / 删除(订单归超管)
   → 超级管理员自身：不可删除/停用，仅自助改密
```

| GET/POST | `/admin/change-password` | 新：自助修改登录密码 | 所有登录管理员 |
| GET | `/admin/orders` | 改：按角色过滤 + 责任人列 | 登录管理员 |
| GET | `/admin/orders/<id>` | 改：按 owner 鉴权（非本人且非超管 → 403） | 登录管理员 |
| POST | `/order/create` | 改：读归属写 `owner_admin_id` | 公开 |

> 技术注意：`/<短码>` 使用「4-6 位纯数字」路径转换器约束，与 `/admin`、`/order`、`/enter`、`/uploads` 等既有字母路径天然不冲突。

## 13. 实施分期建议

1. **阶段 1（模型 + 迁移）**：`admin.py`/`order.py` 加字段 → `migration.py` v2 → `_seed` 写死超级管理员。先在旧库副本验证迁移。
2. **阶段 2（登录 + 术语统一）**：改「登录密码」文案，登录校验角色与 `is_active`。
3. **阶段 3（管理员管理 + 专属短码）**：管理员 CRUD + `/<短码>` 路由 + 「我的专属链接」页 + 自助改密。
4. **阶段 4（归属 + 隔离 + 责任人展示）**：下单写 owner、列表/详情隔离、责任人列。
5. **阶段 5（加固）**：CSRF、鉴权 403、责任人筛选。
6. **阶段 6（验收）**：按 §6 验收清单回归，同步 docs 与 README。

> 建议本次同时把 P0 技术债（备份/systemd/HTTPS）与 CSRF 纳入排期，避免「新功能上线 + 旧风险叠加」。
